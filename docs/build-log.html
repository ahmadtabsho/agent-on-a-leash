1 — The task

Decide whether an AI agent may spend a customer's money

An AI shopping assistant can now pay with a real card. This builds the layer in between — the one that looks at each proposed purchase and returns approve, decline, or ask the customer, inside eight seconds, with the evidence attached.

Not the shopping agent. Not the payment. Just the decision, and the customer's control over it.

A hosted sandbox, and a simulator

15 endpoints covering the mandate lifecycle, run control, long-polling and decisions — plus the simulator that plays the shopping agent. The brief names three things explicitly outside our scope: the agent, payment processing, and merchant databases.

What the platform does not do.

It stores hard_rules and an uncertainty_policy — and never evaluates either. The contract says a rule's field is "a convention for your engine to interpret, not a formula the API runs."

It is a filing cabinet and a delivery mechanism. Every judgement in this system is ours.

6 — What broke

Six bugs the fixtures and the live API caught

Four came from running the supplied data rather than reading it. One came from a test. One came from first contact with the real service.

  1. The spending limit let through the purchase that broke itA rolling limit compared only prior spend, so CHF 299.50 + 65.50 sailed past a CHF 300 cap and the next order got blamed.
  2. "The seller didn't say" was treated as "no"An unstated return policy was declining. It is not permission — but it is not a refusal either.
  3. A trail shoe passed as a road-running shoeIts description advertises a "lugged off-road sole", and the matcher was reading marketing copy as identity.
  4. "Pause" was being read as "refuse"An unfamiliar device is a new laptop as often as it is an intruder. Signals resting on a guess now ask rather than block.
  5. Our own output failed our own contractThe serialiser wrote amounts as strings, so an event saved and reloaded no longer validated.
  6. The envelope from the live service did not parseevent_id arrives as an integer. A real captured envelope is now a test fixture so the next drift shows up in the suite.

7 — The four decisions

What makes it a leash rather than a formality

None of these are in the contract. All of them are what the challenge is actually grading.

Merchant text is read, never obeyed.

Facts are pulled out by pattern, and a pattern can only yield a number or a word — so no phrasing produces permission. The scanner holds no reference to the policy, so by construction nothing a shop writes can reach the verdict.

"Uncertain" is a separate answer from "no".

Collapsing them one way blocks ordinary shopping; the other way waves through what nobody checked. When a fact cannot be established, the customer's own stated preference decides.

A policy can only ever be tightened.

Rules combine with AND, so an addition can only narrow what is allowed. Adding ≤ CHF 200 over ≤ CHF 120 does not raise the limit — and the customer is told that rather than left believing it did.

The model cannot approve anything.

It answers one question, never sees the policy, and can only raise doubt. A test proves a broken model gives identical decisions to no model at all.

8 — What is left

What we still need to do

Ordered by what it would cost if it bit during judging.

Only a person can do these

  • Stress the policy compiler with your own sentencesThe weakest link in the chain, and the one nobody but you can test — run leash policy "your wording" on the phrasings you will actually use in the demo. A wrong reading found now is cheap; found on stage it is not.
  • Rehearse the demo once, timedDecide whether you are presenting from the browser or the terminal, and know how long it takes.
  • Check the two names on the team slide"Ahmad" (not Ahmed) was used, matching the GitHub and git identity. "Wictor" was kept exactly as supplied, though the photo file says viktor.

Code gaps, in order

  • GET /v1/events reconciliationThe client method exists; nothing calls it. It would matter for recovering cleanly from a network drop mid-run rather than relying on redelivery alone.
  • No UI for adding a brand-new ruleThe API supports tightening with add_rules; the interface only exposes the one-click "refuse when unsure". A judge asking "can I lower my limit mid-run?" gets a curl command, not a button.
  • Two numbers are judgements, not measurementsMerchant familiarity is ≥ 1 prior approved purchase; the duplicate window is 3 hours. Both work on the supplied data; neither is derived from anything. The compiler does explicitly ask the customer to set the first.
  • The advisor has never called a real modelEvery failure path is tested; the happy path against a live endpoint is not. It is off by default, so this only matters if you want to demo it.
  • Familiarity loads all 4,701 history rows at importCorrect at this size, wrong shape at real scale — it should be an index or a query.
