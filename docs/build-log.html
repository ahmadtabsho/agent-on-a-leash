The task

Decide whether an AI agent may spend your money

An AI shopping assistant can now pay with a real card. This builds the layer in between — the one that looks at each proposed purchase and answers approve, decline, or ask the customer, inside eight seconds, with reasons attached.

Not the shopping agent. Not the payment. Just the decision, and the customer’s control over it.

What was built

Nine steps, in order

1Repo & data pack. Vendored the 45 purchases and 4,701 history rows; every file checked against its manifest by sha256.
2Typed contract. Strict parsing against the platform’s own schema. Money is Decimal, never float.
3Policy compiler. A sentence becomes executable rules, plain-English guidance, and the questions it refuses to answer for you.
4Decision engine. Seven stages, pure function, no network. All 45 purchases decided in under a millisecond each.
5Replay harness. Runs every scenario offline with no API key, journalling each decision so a crash cannot reset the budget.
6Sandbox worker. Long-polls the Viseca API and answers each purchase; a repeat delivery replays the saved answer.
7Control interface. React + a separate API. Draft, confirm, run, pause, answer, tighten, revoke.
8Optional model. A second opinion on one narrow question. Off by default, and unable to approve anything.
9Demo & docs. The three moments the brief asks to show, picked from a live run rather than scripted.

What broke

Five bugs the fixtures caught

The first engine looked right and was wrong in four places. All four were found by running the supplied data, not by reading the code.

  1. The spending limit let through the purchase that broke itA rolling limit compared only prior spend, so CHF 299.50 + 65.50 sailed past a CHF 300 cap and the next order got blamed.
  2. “The seller didn’t say” was treated as “no”An unstated return policy was declining. It is not permission — but it is not a refusal either. It goes to the customer.
  3. A trail shoe passed as a road-running shoeIts description advertises a “lugged off-road sole”, and the matcher was reading marketing copy as identity.
  4. “Pause” was being read as “refuse”An unfamiliar device is a new laptop as often as it is an intruder. Signals that rest on a guess now ask rather than block.
  5. Our own output failed our own contractFound by a test. The serialiser wrote amounts as strings, so an event saved and reloaded no longer validated.

Three decisions

The choices that shape everything else

Merchant text is read, never obeyed.

Product descriptions are useful (size, return window) and written by whoever wants the payment approved. Facts are pulled out by pattern — a pattern can only yield a number or a word, so no phrasing produces permission. The scanner holds no reference to the policy, so by construction nothing written in a shop’s description can reach the verdict.

“Uncertain” is a separate answer from “no”.

Most of the work is keeping those apart. Collapsing them one way blocks ordinary shopping; the other way waves through things nobody checked. When the engine cannot establish a fact, the customer’s own stated preference decides.

The model cannot approve anything.

It answers one question, never sees the policy, and can only raise doubt — never resolve it. The worst a broken or hostile model can do is send a purchase to the customer. A test proves a broken model gives identical decisions to no model at all.

Still open

What is honestly not done

  • Nothing has touched the live API. Every endpoint is written and tested against a mock, but the team key arrives on event day. Only /healthz has been hit for real.
  • The control session is in-memory. Fine for a demo; a real deployment needs the policy and inbox to survive a restart. The decision journal already does.
  • Two numbers are judgements, not measurements — the familiarity threshold (one prior purchase) and the duplicate window (three hours).
  • The optional model has never called a real endpoint. Every failure path is tested; the happy path is not.

Seeing it

Three commands

make demo      # the three moments the brief asks to show
make replay    # all 45 purchases, every decision and why
make serve && make ui   # the interface on localhost:5173

No API key needed for any of it — the supplied scenarios run entirely offline. The full walkthrough, with the pipeline explained stage by stage, is in docs/pipeline.html.
