01 — The problem

A blank cheque, handed to software

Visa and Mastercard have both shipped the rails for an AI agent to pay with your card. The agent is the easy part. The hard part is the thing that sits between it and your money.

You tell an assistant: “Buy me black running shoes for up to CHF 200.” Four things can now go wrong, and they fail in different directions:

  • It spends too much — not by ignoring your limit, but by splitting an order, or adding delivery, or buying twice.
  • It buys from a shop you would not have chosen — often one whose name is one letter from a shop you would.
  • It buys the wrong thing — a trail shoe instead of a road shoe, size 42 instead of 43, a gift voucher instead of a monitor.
  • It gets talked into it — because the shop writes the product description, and the product description is an input to whatever is reading it.

What this project builds is the control layer that answers one question per purchase, inside eight seconds, with reasons attached. Not the agent. Not the payment. Just the decision.

02 — Shape of the answer

Two deployables, one contract

Viseca intends to fold wallet-control configuration into the existing one app, while the approve/decline/ask decision runs in the backend under a hard latency ceiling. Those halves have opposite requirements — one is interactive and redeployed freely, the other is a hot path measured in milliseconds — so they are separate services that share only an HTTP contract. The engine never imports from the control plane; the control plane calls into the engine.

The engine is a pure function of (event, run state). No network, no clock beyond what it is handed, no I/O.

That single constraint is what makes it fast enough for the deadline, testable offline against all 45 supplied purchases, and impossible for a merchant to talk out of an answer — there is nothing to talk to.

03 — The seven stages

How one decision is produced

Stages run in order. Each appends to a shared evidence ledger, and the verdict is derived from the ledger at the end rather than returned early from the middle — so the explanation always accounts for everything that was looked at.

1

Parse and validate

Two gates: the platform’s own authorization_event.schema.json, then typed models in Pydantic strict mode. Every problem is reported at once, never a partial parse.

Prevents "20.00" silently becoming a number, 5411 passing as a four-digit MCC string, and True counting as an integer because Python says bool is an int.

2

Platform preconditions

Mandate status, authority status, card status, and that the purchase is even on the card the customer authorised. These are facts, not judgement calls — anything not active is a decline.

Prevents spending on a permission the customer already withdrew.

3

Sanitise merchant text

Product copy is mined for facts and scanned for instructions aimed at an automated decider. The sanitiser returns data and holds no reference to the policy.

Prevents a product description raising a spending limit. By construction, not by vigilance.

4

Hard rules

The customer’s confirmed checks, combined with AND. A breach is a decline — except on fields that rest on an inference rather than a fact, which escalate instead.

Prevents a period limit measured on prior spend alone, which approves the very purchase that breaks it and catches the next one.

5

Intent match

Does the basket contain what was actually asked for? Identity comes from the item name and category only. Product prose is read for attributes like size, never for identity.

Prevents a trail shoe advertised with a “lugged off-road sole” passing as the road-running shoe that was requested.

6

Behavioural signals

Device novelty, velocity, merchant familiarity from 4,701 historical rows, lookalike shop names, duplicate baskets under a new ID, unrequested additions, recurring commitments, totals that do not reconcile.

Prevents matching familiarity on a shop name — the one field an impostor controls.

7

Resolve

A definite breach declines. Anything left unsettled falls to the customer’s own uncertainty_policy. Only a clean pass approves.

Prevents collapsing “uncertain” into either neighbour — which is how a control layer ends up blocking ordinary shopping, or waving through something nobody checked.

Why the third outcome carries the weight

Most of the engineering here is keeping UNCERTAIN distinct from FAIL. PASS and FAIL are claims about the purchase. UNCERTAIN is a claim about us: we could not establish the fact.

When a seller states no return window, they have not offered a zero-day one. That is not permission and it is not a refusal — and the brief is explicit that unknown must never be “silently dropped, changed to zero, or treated as permission”. It is exactly the case the customer had in mind when they wrote “ask me when uncertain”, so it goes to them.

04 — Compiling a policy

Turning a sentence into checks, and admitting what it does not settle

The compiler takes the customer’s own words and produces three things. The third matters as much as the first.

OutputWhat it is for
hard_rulesExecutable checks, in the API’s stored rule format.
guidanceWhat we understood, in plain language, before anything is spent.
open_questionsWhat the sentence does not settle — and we refuse to settle for them.

Extraction is deterministic pattern matching. No model is involved: compilation happens once, before confirmation, and the same sentence must always produce the same rules. Here is SCEN0002 in full:

// "Replace my worn road-running shoes in size 43. Buy only from a
//  specialist sports retailer, only if the order can be returned
//  within 14 days or more, and pay no more than CHF 200."

authorization.billing_amount_chf          <=  200.0   CHF, purchase
authorization.merchant.merchant_category  in  [sporting_goods]
derived.return_window_days                >=  14
authorization.order_returnable            =   "true"
derived.requested_item                    =   "road-running shoes"
derived.requested_attribute               =   "size=43"
derived.requested_item_match              =   "match"

Two modelling calls worth naming

A purpose-category constrains the basket; a retailer-type constrains the shop. “Household groceries” compiles to a rule over items[], because a supermarket sells cosmetics without ceasing to be a grocery merchant. “Specialist sports retailer” compiles to a rule over merchant_category. The pack’s own data dictionary confirms the split independently: cosmetics, gift_card and membership exist as item categories with no merchant counterpart at all.

The field namespace is closed. A rule’s field is, in the platform’s words, “a convention for your engine to interpret”. That freedom is also a hazard — a field name nothing resolves is a rule that silently never fires — so all 19 fields are declared, and every compiled rule is checked against them.

What it refuses to decide

“A shop I use regularly” has no field in the event. Somebody has to decide whether regularly means one past purchase or five, and that somebody is the customer. Quietly picking a threshold would be the exact failure this challenge is about.

One question the instructions never raise but the data does — added after noticing AU0005 and AU0006 sitting six minutes apart:

“Two orders placed minutes apart at the same shop can each stay under CHF 120 while together going over it. Should closely spaced orders from one shop be treated as a single order, or brought to you?”

Amendments can only tighten

The platform enforces part of this: a PATCH must keep every existing rule, and uncertainty_policy may only move toward decline. But the brief asks for more — adding a rule must not weaken an existing restriction. The guarantee comes from conjunction: every rule ANDs, so an addition can only remove purchases from the allowed set.

One consequence is worth stating plainly. Adding <= CHF 200 on top of <= CHF 120 does not raise the limit; 120 still binds. That is correct, and it is not what a customer expects, so the review returns “the existing limit still governs — revoke and re-authorise if you meant to relax it” rather than letting them believe otherwise.

05 — Untrusted text

Read the shop’s words. Never take orders from them.

item_details is genuinely useful — shoe size, panel size, return window — and it is written by whoever wants the payment approved. Those two facts are only in tension if the text is obeyed.

So the module does two separate things and keeps them separate. Facts are extracted by pattern, and a pattern can only ever yield a number or a token — no phrasing produces a permission. Separately, text addressed to an automated decider is detected across six independent signatures, after folding zero-width joiners, bidirectional overrides and full-width characters that would otherwise hide it.

A detection cannot change a rule — nothing here can reach the policy. What it does change is trust in the rest of that seller’s copy, and it is a signal the customer should see in its own right.

06 — Money and time

Two clocks, one currency, no floats

Spending limits are the spine of the challenge, so money never touches binary floating point. Amounts are Decimal, quantised to two places with half-even rounding, converted at the pack’s fixed rates — read from fx_rates.csv rather than hard-coded.

RuleWhy it exists
Convert with the row’s currency, never the merchant’s countryA CHF amount does not imply a Swiss merchant, and 61 historical rows at foreign merchants bill in CHF because the cardholder accepted conversion at the till.
amount already includes deliveryAdding delivery_fee again would push AU0003 — CHF 114 of goods plus CHF 6 delivery, exactly at a CHF 120 limit — over the line.
Windows run on authorization.timestampSimulated purchase time. deadline_at is the real clock and governs only the response.
Only final approvals count as spendA purchase waiting for a human answer is not yet spent. It is tracked separately and moves only when the customer answers.

Both money invariants are verified against every one of the 45 attempts as tests: our CHF conversion reproduces the platform’s billing_amount_chf exactly — including 219.00 GBP → 245.28 and 450.00 USD → 391.50 — and items_subtotal + delivery_fee equals amount on every row.

08 — Five real bugs

Found by running the fixtures, not by reading them

The first implementation of the engine looked plausible and was wrong in four places. Each one is recorded here because each one is a trap the next person will hit.

A period limit that excluded the order being decided

Comparing prior spend alone approved the purchase at CHF 299.50 + 65.50 = 365 against a CHF 300 cap, then declined the next one. “Keep the total across any seven days at or below CHF 300” is a claim about the total including this order.

AU0008 · decision/facts.py

order_returnable: "unknown" was declining

The seller not stating a term is not permission — but it is not a refusal either. Reading it as a failed comparison turned “we could not tell” into “the customer forbade it”.

AU0016 · decision/facts.py

A trail shoe passed as a road-running shoe

Its product copy advertises a “lugged off-road sole”, and the matcher was reading prose as identity. Identity now comes from the item name and category only.

AU0017 · decision/facts.py

A session signal was declining, not pausing

The customer wrote “Pause anything that looks like someone other than me is driving the session.” An unfamiliar device is a new laptop as often as it is an intruder. Fields resting on an inference now escalate rather than refuse.

AU0026 · policy/vocabulary.py

Our own serialiser produced invalid events

Found by a test, not by a fixture. Pydantic writes Decimal as a JSON string, so an event round-tripped through model_dump came back failing the schema it was built from.

09 — When things fail

Every failure has a defined answer

“The system must function if optional models fail” is the stated requirement. In practice the harder half is everything else that can fail.

FailureBehaviour
The model is slow, absent, or returns junkDropped. Stages 1–7 run unchanged and produce the decision.
An event fails the contractEscalated with the parse errors attached. Never decided on.
A rule names a field we cannot resolveUncertain — never silently satisfied.
A fact cannot be establishedUncertain — never read as permission, never as refusal.
The same purchase is delivered twiceRecognised by live authorization_id; the saved answer is re-sent. Spend is not double-counted.
An empty poll (204)No work in that window — not the end of the run. Poll again.
The worker restarts mid-runSpend totals and answered IDs rebuild from the append-only journal. A crash must not hand the agent a fresh budget.
A paused purchase, at restartRecovers as still pending — not as spend.

10 — The optional model

A second opinion that cannot become a dependency

The brief allows language models in the decision path and prefers small, fast ones. It also requires predictability when they fail. Those two together dictate a deliberately small module.

  • One question only. Is this cart line the thing the customer described? That is the one judgement where token matching genuinely struggles. Limits, categories, return windows and session signals are decided arithmetically and never consult a model.
  • It never sees the policy. It is given the product facts and nothing else. A model that cannot see the limits cannot be talked into raising them.
  • It is one-directional. It can turn an apparent match into uncertainty. It can never turn uncertainty into a match.

The worst a wrong or compromised model can do is send a purchase to the customer — which is what the system already does when it is unsure.

It cannot approve anything.

Every failure path returns nothing: no key, no network, a timeout, prose instead of JSON, a verdict outside the three accepted, a reply that arrives after the budget. A test asserts that a broken model produces identical decisions to no model at all, across all five scenarios.

11 — Running it

What is where, and how to drive it

engine/src/leash/models/The typed contract. Strict parsing, Decimal money, closed vocabularies.
engine/src/leash/policy/Instruction → rules, guidance, open questions. Tighten-only amendments.
engine/src/leash/decision/The pure engine: sanitiser, fact resolvers, rule evaluation, run state, history.
engine/src/leash/replay/Offline event assembly from the CSVs, the harness, the append-only journal.
engine/src/leash/api/Sandbox client, and the control API the interface talks to.
engine/src/leash/worker/The long-poll loop, idempotency, the step-up inbox.
engine/src/leash/llm/The optional advisor. Deletable without changing a decision.
ui/React control surface: policy composer, decision timeline, step-up inbox.
data/The vendored pack, verified against its manifest by sha256 on every run.

make test      # 207 tests

Without a team key the entire flow — draft, confirm, run, pause, resolve, tighten, revoke — runs against the vendored scenarios. The control loop is demonstrable today, not on the event morning.

12 — Not built yet

What is honestly still open

  • Nothing has touched the live API. Every keyed endpoint is written and unit-tested against a scripted transport, but the team key arrives on the event day. /healthz is the only endpoint actually exercised against the running service.
  • The control session is in-memory. Fine for a prototype and a demo; a real deployment needs the mandate and the inbox in a store that survives a restart. The decision journal already does.
  • Familiarity uses one prior purchase as its threshold. That is the reading that does not invent a relationship the history does not show — and the compiler asks the customer to set it properly rather than leaving it to us.
  • The advisor has never called a real model. It is off by default and every failure path is tested; the happy path against a live endpoint is not.
  • Duplicate detection has one tunable — a three-hour window. It catches the repeated basket in the pack and lets the legitimate re-quote through, but the number is a judgement, not a measurement.
