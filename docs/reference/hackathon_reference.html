🎯 Challenge Objective

Build a prototype wallet control layer that decides whether an AI shopping agent may spend a customer's money.

The Wallet Control System

The wallet control layer is configured through a customer-managed wallet policy and operates independently of the AI shopping agent and its shopping instructions.

Key Workflow

  1. Customer (card owner) sends a shopping request to the AI shopping agent
  2. Customer separately defines the wallet policy directly with Wallet Control
  3. AI shopping agent forwards the proposed transaction (with payment context) to Wallet Control
  4. Wallet Control evaluates the transaction against the wallet policy
  5. Returns a decision: approve, decline, or ask (step up for human confirmation)
  6. This leads to the final outcome

What You Build vs. What You Don't

✅ You Build:

  • The wallet control layer
  • Policy interpretation logic
  • Transaction evaluation
  • Human escalation paths

❌ You Don't Build:

  • The shopping agent itself
  • Payment processing
  • Merchant databases
  • Card authorization systems
Key Rule: Do not hard-code decisions to scenario names, request IDs, or sequence positions. Build a flexible, policy-driven system.

✅ Key Requirements

Must-Have Capabilities

  • Policy Translation: Translate customer input (rules or natural-language wallet policy) into clear, executable permissions
  • Policy Management: Customer can tighten, update, or revoke the wallet policy
  • Transaction Evaluation: Evaluate each proposed transaction against the wallet policy
  • Decision Engine: Return one of three decisions for each transaction:
    • Approve: Transaction meets policy
    • Decline: Transaction violates policy
    • Ask (Step-Up): Ambiguous or unusual - escalate to human for decision

Transparency & Auditability

Judges must be able to understand:
  • What the system permitted
  • What evidence it considered
  • Why it acted
  • How the customer retained control

Resilience Requirements

  • Works with supplied synthetic data and simulator
  • Responds within required deadline
  • Remains predictable if optional models or external services fail
  • Does not expose hard-coded scenario assumptions

🏗️ System Architecture

System Overview (Deep Dive)

Customer (card owner) sends a shopping request to the AI shopping agent and separately defines the wallet policy directly with Wallet Control. The AI shopping agent forwards the proposed transaction together with payment context to Wallet Control. Wallet Control evaluates the transaction against the wallet policy and returns a decision: approve, decline, or ask, leading to the final outcome.

See attached architecture diagram in Github Repo for visual representation of system flow.

Technical Preferences & Constraints

Viseca's Intent: Integrate control-layer configuration into the existing Viseca one mobile app, while the decision (approve/decline/ask) must meet strict latency requirements and runs in the backend.

Recommended Approach: Decouple the wallet-control user interface from the engine that approves, blocks, or escalates transactions. This allows each component to be integrated, deployed, and scaled independently.

Model Preferences

  • If language models are used in the decision path: smaller, lower-latency models are preferred
  • Prioritize latency and reliability over model sophistication
  • System must function if optional models or external services fail

Deployment Flexibility

  • Wallet-control UI integrates with Viseca one mobile app
  • Decision engine runs independently in backend
  • Each component can be deployed and scaled independently
  • No tight coupling between UI and decision logic

🎬 Demonstration Criteria

You Must Demonstrate

All three scenarios:
  1. Ordinary Transaction (No Friction):
    • One straightforward transaction that completes with minimal friction
    • System approves based on policy
  2. Ambiguous/Unsafe/Manipulated Transaction (Useful Intervention):
    • One suspicious, ambiguous, or manipulated transaction
    • System detects issue and provides useful intervention
    • Could be asking human for approval or declining with clear reason
  3. Human Approval/Rejection/Revocation Path:
    • Demonstrate the human decision path
    • Show how customer approval, rejection, or revocation affects system behavior

Judge Evaluation Criteria

Judges need to understand:

  • What the system permitted
  • What evidence it considered
  • Why it acted the way it did
  • How the customer retained control
