01 — The problem

A blank cheque, handed to software

Visa and Mastercard have both shipped the rails for an AI agent to pay with a real card. The agent is the easy part. The hard part is what sits between it and the money.

A customer says: “Buy me black running shoes for up to CHF 200.” Four things can now go wrong, and they fail in different directions:

  • It spends too much — not by ignoring the limit, but by splitting an order, adding delivery, or buying twice.
  • It buys from a shop they would not have chosen — often one whose name is a single letter from a shop they do use.
  • It buys the wrong thing — a trail shoe instead of a road shoe, size 42 instead of 43, a voucher instead of a monitor.
  • It gets talked into it — because the shop writes the product description, and that description is an input to whatever reads it.

Our deliverable answers one question per purchase, inside eight seconds, with reasons attached. Not the agent. Not the payment. Just the decision, and the customer’s control over it.

The pack carries no expected decisions, no risk labels and no answer key. Historical status is what happened at the time, not a verdict. The brief names three things explicitly outside scope: the shopping agent, payment processing, and merchant databases.

The platform stores the policy. It decides nothing.

It accepts hard_rules and an uncertainty_policy, and never evaluates either. The contract is explicit that a rule’s field is “a convention for your engine to interpret, not a formula the API runs”. It is a filing cabinet and a delivery mechanism. Every judgement in the system is ours.

03 — Architecture

Two deployables, one contract

Viseca intends to fold wallet control into the existing one app, while the decision runs in the backend under a hard latency ceiling. Opposite requirements, so they are separate services that share only an HTTP contract.

  Control UI  →  Control API  →  Decision engine  →  Viseca sandbox
   (React)       (FastAPI)         (pure, <3 ms)
                      ↑                ↑
                   Worker      Run state & journal
              (long-poll loop)  (spend, answered ids, baskets)

Dependencies point one way only, verified by grepping the import graph: models/, policy/ and decision/ never import api/ or worker/, and contain no HTTP client at all.

The engine is a pure function of (event, run state).

No network, no clock beyond what it is handed, no I/O. That single constraint is what makes it fast enough for the deadline, testable offline against all 45 supplied purchases, and impossible for a merchant to talk out of an answer — there is nothing to talk to.

04 — The decision

Seven stages, in order

Each appends to a shared evidence ledger. The verdict is derived at the end rather than returned from the middle, so the explanation always accounts for everything that was looked at.

1Parse and validateTwo gates: the platform’s own JSON Schema, then strict typed models. A message we cannot fully read is never decided on.
2PreconditionsMandate, authority and card status, and that the purchase is even on the authorised card. Facts, not judgement calls.
3Sanitise merchant textRead it for facts; never obey it. The sanitiser returns data and holds no reference to the policy.
4Hard rulesThe customer’s confirmed checks, combined with AND, so an addition can only narrow what is allowed.
5Intent matchIs the basket what was actually asked for? Identity comes from the item name and category, never product prose.
6Behavioural signalsDevice novelty, velocity, merchant familiarity, lookalike names, duplicate baskets, unrequested additions.
7ResolveA breach declines. Anything unsettled falls to the customer’s own uncertainty policy. Only a clean pass approves.

Why the third outcome carries the weight

Most of the engineering is keeping UNCERTAIN distinct from FAIL. Pass and fail are claims about the purchase. Uncertain is a claim about us: we could not establish the fact.

When a seller states no return window, they have not offered a zero-day one. That is not permission, and it is not a refusal. The brief is explicit that unknown must never be “silently dropped, changed to zero, or treated as permission” — so it goes to the customer, which is exactly what they asked for when they wrote “ask me when uncertain”.

05 — Design decisions

What makes it a leash rather than a formality

None of these four are in the contract. All of them are what the challenge actually grades.

1. Merchant text is read, never obeyed.

Product copy is useful — sizes, return windows — and it is written by whoever wants the payment approved. Those are only in tension if the text is obeyed. Facts are extracted by pattern, and a pattern can only ever yield a number or a token, so no phrasing produces a permission. The scanner has no access to the policy, so by construction nothing a shop writes can reach the verdict.

2. “Uncertain” is a separate answer from “no”.

Collapsing them one way blocks ordinary shopping, which the brief counts as a failure. The other way waves through what nobody checked. When a fact cannot be established, the customer’s own stated preference decides.

3. A live policy can only ever be tightened.

Rules combine with AND, so an addition can only remove purchases from the allowed set. Adding ≤ CHF 200 over an existing ≤ CHF 120 therefore does not raise the limit — and the customer is told that rather than left believing it did.

4. The optional model cannot approve anything.

It answers one question, never sees the policy, and is one-directional: it can turn an apparent match into uncertainty, never the reverse. The worst a wrong or compromised model can do is send a purchase to the customer.

Bootstrap confirmed everything else we had built on: the 8-second decision budget, the 120-second human window, the 25-second long poll, and mandate_patch_tighten_only: true. One operational note: /v1/team/reset is disabled during judging, so no demo may depend on it.

The timeout question, answered by measurement

The obvious implementation is to auto-decline when the customer does not answer. That would have been wrong twice: the guide forbids inventing a human answer, and a decline we submit would be recorded as the customer’s decision when they never made one. It would also have overwritten the platform’s own correct handling.

Lapsing is the absence of an answer, not an answer. The purchase leaves the inbox, was never approved, never counted as spend, and a late reply is refused with an explanation rather than failing silently.

08 — What broke

Eight defects, and how each was caught

Most were found by running the supplied data rather than by reading the code. They are recorded because each is a trap the next implementer will hit.

A period limit excluded the order being decidedComparing only prior spend approved the purchase at CHF 299.50 + 65.50 against a CHF 300 cap, and blamed the next one. A rolling limit is a claim about the total including this order.
“The seller did not say” was treated as “no”An unstated return policy was declining. Not permission — but not a refusal either.
A trail shoe passed as a road-running shoeIts copy advertises a “lugged off-road sole”, and the matcher was reading marketing prose as identity.
A session signal was declining, not pausingThe customer wrote “pause”. An unfamiliar device is a new laptop as often as an intruder, so fields resting on an inference now escalate.
Our own serialiser produced invalid eventsDecimal was written as a JSON string, so an event round-tripped through our own code failed the schema it was built from.
The live envelope did not parseevent_id arrives as an integer where the contract gives it no type.
“CHF 300 a week” compiled to a per-order capThe period pattern required a preposition. The effect was not a missing rule but a much weaker one: a weekly budget became a per-order allowance spendable every day.
“Never spend more than CHF 500” produced no limit“More than” reads as a minimum, so the clause was set aside as a question and a stated ceiling was dropped. Negation now wins — without turning a genuine floor into a limit.

09 — The optional model layer

Built, measured, and switchable

The brief permits language models in the decision path, prefers small low-latency ones, and requires the system to stay predictable when they fail. We built the hook and then measured whether it earns its place.

Three providers are supported — OpenRouter, OpenAI and Anthropic — differing only in endpoint and auth. One configuration line switches all of them, and a single helper is the only place a provider, model and key become a callable, so no module can quietly stay on a different vendor.

Two roles

  • Intent advisor. One question: is this cart line the item the customer described? Never sees the policy, one-directional, cannot approve.
  • Policy clarifier. Rewrites a blocking compiler question into one a person can answer, and rewrites the instruction from their reply. Falls back to the deterministic question when unavailable.

Measured against OpenRouter, gpt-4o-mini

MeasureAdvisor offAdvisor on
Slowest decision across 45 purchases0.97 ms3,102 ms
Share of the 8,000 ms budget0.01%39%
Decisions changed—none

A 3,200× latency increase for identical outcomes.

That is the design working, not failing. The advisor can only raise doubt, and on this data the deterministic engine already resolves every case it would have been asked about. A test asserts that a broken model — timeout, prose instead of JSON, an unknown verdict — produces decisions identical to no model at all.

The defensible position: the AI here is the thing being controlled, not the thing doing the controlling. Putting a model in the path that gates spending would be the vulnerability, in a challenge whose whole point is text trying to talk a decider into approving.
