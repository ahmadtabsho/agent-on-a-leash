One item we should not overclaim.

The brief suggests combining “rules-based logic, behavioural signals, machine learning, language models and interface design”. We use four of those five. There is no trained machine-learning model in this system: behavioural signals are computed arithmetically from history rather than learned. We think that is the right call at this data scale — 4,701 history rows is not a training set — but it is a deliberate omission, not an oversight, and we would rather say so than imply otherwise.

03 — The problem

Four safety concerns, one decision

The brief names four things that can go wrong when an agent holds a card. They fail in different directions, and a system that only guards against one of them is not a control layer.

ConcernHow it actually manifests in the dataOur answer
Spending limits
“Doesn't spend too much?”		Not by ignoring a limit, but by splitting an order, by the delivery fee, or by a rolling window nobody is tracking.Decimal arithmetic, rolling windows on simulated purchase time, only final approvals counted.
Merchant vetting
“Doesn't buy from shady merchants?”		The shop is not obviously shady — its name is one letter from one you trust.Familiarity matched on merchant_id, plus similarity detection against names this card has actually used.
Intent verification
“Purchases what you actually intended?”		The right category, the right price, the wrong item. A trail shoe. Size 42. A voucher.Requested-item matching on name and category, attribute extraction from product text, unrequested-line detection.
Prompt injection
“Resilient against injection?”		The shop writes the product description, and that description is an input to whatever reads it.Facts extracted by pattern only; the scanner holds no reference to the policy, so nothing written can reach the verdict.

And the failure mode nobody lists

Blocking ordinary shopping is also a failure.

The brief says it explicitly: “Unfamiliar purchases are not automatically wrong; blocking ordinary shopping unnecessarily is also a failure.” A layer that declines everything scores zero on both counts. Two of the supplied attempts exist purely to catch over-blocking — AU0023, a new but fully compliant seller, and AU0042, a legitimate re-quote after a decline. Both are approved.

04 — Architecture

Two deployables, one contract

Viseca intends to fold wallet control into the existing one app, while the decision runs in the backend under a hard latency ceiling. Opposite requirements, so they never share a process.

The dependency graph points one way only, and this was verified by grepping imports rather than assumed: models/, policy/ and decision/ never import api/ or worker/, and contain no HTTP client at all.

The engine is a pure function of (event, run state).

No network, no clock beyond what it is handed, no I/O. One constraint buys three properties: it is fast enough for the deadline, it is testable offline against every supplied purchase, and it cannot be talked out of an answer because there is nothing to talk to.

05 — The build, step by step

Twelve components, and the reasoning behind each

1. Data pack and integritydatapack.py · 4 tests

The pack is vendored so offline replay needs no network. Every one of its 18 files is verified against the manifest's sha256 and row count on each run.

Why: a silently edited fixture would change decisions without changing code. Failing loudly at load is cheaper than debugging a wrong verdict.

2. The typed contractmodels/ · 16 tests

Two gates on every incoming event: the platform's own authorization_event.schema.json, then Pydantic in strict mode with extra="forbid". All problems are reported at once, never a partial parse.

Strict mode gives the schema's semantics rather than a friendly approximation. "20.00" is rejected where a number is required. 5411 is rejected for merchant_mcc, which the schema pins as a four-digit string. True is rejected wherever an integer is required, because Python treats bool as int and the schema does not.

Three semantics the schema cannot express, added on top: order_returnable stays a four-valued string, so “unknown” never becomes “yes”. A null period spend stays null, never 0.0, which would invent headroom. Naive timestamps are rejected, because a spending window computed against a zoneless time is a quietly wrong window.

3. The policy compilerpolicy/compiler.py · 39 tests

Turns the customer's own sentence into three outputs. hard_rules are executable. guidance is what we understood, in plain language. open_questions is what the sentence does not settle — and we refuse to settle it for them.

Extraction is deterministic pattern matching, no model. Compilation happens once, before confirmation, and the same sentence must always produce the same rules, because a customer confirming a policy is agreeing to those rules.

Example — SCEN0002 compiles to 7 rules: billing_amount_chf <= 200, merchant_category in [sporting_goods], return_window_days >= 14, order_returnable = true, requested_item = "road-running shoes", requested_attribute = size=43, requested_item_match = match — plus 4 open questions.

What it refuses to decide. “A shop I use regularly” has no field in the event. Somebody must decide whether regularly means one past purchase or five, and that somebody is the customer. We also surface a gap the instructions never mention but the data does: two orders minutes apart can each sit under a per-order cap while together clearing it.

4. The field namespacepolicy/vocabulary.py · 19 fields

A rule's field is, in the contract's words, “a convention for your engine to interpret”. That freedom is also a hazard: a field name nothing resolves is a rule that silently never fires. So the namespace is closed, declared, and every compiled rule is checked against it.

Each field declares how it resolves — straight off the event, across every cart line, or derived from history, run state or merchant text — and whether a breach declines or escalates.

Only one field escalates on breach: derived.session_integrity. Whether someone other than the cardholder is driving a session is an inference, never something the evidence settles. An unfamiliar device is a new laptop as often as an intruder, and customers phrase that constraint as “pause”.

5. The decision enginedecision/engine.py · 34 tests

Seven stages in order, each appending to a shared evidence ledger. The verdict is derived from the ledger at the end rather than returned early from the middle, so the explanation always accounts for everything looked at.

#StageWhat it prevents
1Parse and validateDeciding on a message we could not fully read
2PreconditionsSpending on a permission already withdrawn
3Sanitise merchant textA product description raising a spending limit
4Hard rulesA period limit measured on prior spend alone
5Intent matchA trail shoe passing as a road shoe
6Behavioural signalsMatching familiarity on a name an impostor controls
7ResolveCollapsing “uncertain” into either neighbour

Resolution rule: a definite breach declines; anything unsettled falls to the customer's own uncertainty_policy; only a clean pass approves.

6. The sanitiserdecision/sanitize.py · 13 tests

item_details is genuinely useful — shoe size, panel size, return window — and it is written by whoever wants the payment approved. Those two facts are only in tension if the text is obeyed.

So the module does two separate things and keeps them separate. Facts are extracted by pattern, and a pattern can only ever yield a number or a token, so no phrasing produces a permission. Separately, text addressed to an automated decider is detected across six independent signatures, after folding zero-width joiners, bidirectional overrides and full-width characters that would otherwise hide it.

Signatures: addresses_automated_agent · impersonates_system_role · overrides_prior_instructions · claims_pre_authorisation · demands_immediate_approval · raises_or_removes_a_limit

False positives matter as much. A test asserts that exactly 2 of 56 supplied cart lines flag. Ordinary copy — “Road-running shoe, size 43; returns accepted within 30 days” — passes untouched.

7. Money and timemodels/money.py · 6 tests

Spending limits are the spine of the challenge, so money never touches binary floating point. Amounts are Decimal, quantised to two places with half-even rounding, converted at the pack's fixed rates read from fx_rates.csv rather than hard-coded.

Two clocks are kept apart. authorization.timestamp is simulated purchase time and drives every spending window, velocity count and familiarity calculation. deadline_at is the real clock and governs only the response.

Both money invariants are verified against all 45 attempts as tests: our CHF conversion reproduces the platform's billing_amount_chf exactly (219.00 GBP → 245.28, 450.00 USD → 391.50), and items_subtotal + delivery_fee equals amount on every row — so adding delivery again would double-charge.

8. Run memorydecision/state.py · 10 tests

Three things survive between purchases, each mapping to a documented failure mode. Approved spend, counting only final approvals — a purchase awaiting a human is not yet spend, and is tracked separately. Answers already given, keyed by live authorization_id, so a redelivery replays the saved answer rather than charging the limit twice. Basket fingerprints, because “different IDs can still describe an unwanted duplicate order”.

The platform redelivers after 3 seconds, which we learned from /v1/bootstrap rather than from the written contract.

9. Offline replay and the journalreplay/ · 10 tests

The pack ships a readable copy of one attempt, not a live event — it has string amounts and a flat shape, and it does not validate against the schema. So offline events are assembled from the CSVs instead, following the documented conversion rules, with fresh real-clock deadlines and live IDs minted per run.

Every decision is journalled append-only with its full evidence. A worker that restarts rebuilds spend totals and answered IDs from it, because coming back with an empty total would hand the agent its budget a second time.

10. Sandbox client and workerapi/ + worker/ · 55 tests

All 15 endpoints. The worker answers what it is handed and never waits on a person. A 204 means no work in that polling window, not that the run ended. A step_up queues the purchase and the reply goes back through /resolve, never as a second automated decision. An event failing the contract is escalated with the parse errors attached rather than decided on.

leash run does the whole live sequence in one command, with two orderings enforced by tests: the worker exists before the run starts, because the eight-second deadline runs from queueing; and nothing runs before the policy is confirmed.

11. Control plane and interfaceapi/control.py + ui/ · 24 tests

A separate FastAPI service and a React interface that talks only to it. The engine never imports from the control plane; the control plane calls into the engine.

Built around the order of authority rather than around screens: an instruction is compiled and shown back with its rules, its plain-language reading and its open questions; nothing runs before confirmation; a live policy can be tightened and never loosened; a paused purchase sits in an inbox that says plainly it is not approved and does not count against a limit.

The session — mandate, inbox, runs and journal — is written atomically to disk on every change and restored on startup. Anything unreadable is discarded rather than half-restored.

12. The optional model layerllm/ · 25 tests

Three providers, differing only in endpoint and auth. Two roles: an intent advisor that gives a second opinion on whether a cart line is the item described, and a policy clarifier that rewords a blocking compiler question and rewrites the instruction from the customer's answer.

Both are constrained the same way. The advisor never sees the policy and is one-directional — it can turn an apparent match into uncertainty, never the reverse. The clarifier changes wording only; code decides when to ask and which answers are acceptable.

Every failure path returns nothing: no key, no network, a timeout, prose instead of JSON, a verdict outside the three accepted, a reply arriving after the budget. One budget covers a whole event, not one per cart line.

Stage 3 has no model, and that is the deliberate part.

Using a language model to detect prompt injection means feeding attacker-controlled text to a model whose output then influences a decision — which is the exact vulnerability the challenge is testing. A regular expression can only ever emit a number or a token, so there is no phrasing that turns into a permission. The scanner also holds no reference to the policy, so there is no code path from merchant text to the verdict at all.

The money is irrelevant: four hundredths of a cent per call, under two dollars for a thousand full runs. The latency is not. That is why the advisor ships off by default, with a test asserting that a broken model produces decisions identical to no model at all.

08 — Anticipated questions

What judges are likely to ask

“Where is the AI?”

The AI is the thing being controlled, not the thing controlling. We built the model hook, measured it, and found the deterministic engine did not need it: slowest decision went from 0.97 ms to 3,102 ms — 39% of the platform's budget — and not one decision changed. Putting a model in the path that gates spending would be the vulnerability, in a challenge whose whole point is text trying to talk a decider into approving.

“How do you know it is not hard-coded to the scenarios?”

A test rewrites scenario_id, request_id and replay_order on every event and asserts the decisions are unchanged. Nothing in the engine reads any of the three.

“Why did it decline 23 of 45? Isn't that over-blocking?”

Every decline traces to a stated customer rule, and the evidence panel names which. Two attempts exist specifically to catch over-blocking — a new but compliant seller and a legitimate re-quote after a decline — and both are approved. SCEN0001 declines five in a row only because the customer's own CHF 300 weekly limit was reached.

“What happens if the customer never answers?”

Nothing is sent. We measured the live API: an unanswered purchase moves to timed_out on its own at exactly 120 seconds. A decline we submitted would be recorded as the customer's decision when they never made one — which the guide explicitly forbids. Lapsing is the absence of an answer, not an answer.

“Could a merchant get a purchase approved by writing the right text?”

No, and not because we filter well. The sanitiser returns data and holds no reference to the policy, and facts are extracted by patterns that can only yield a number or a token. There is no code path by which merchant text reaches the verdict.

“What is the weakest part?”

The instruction compiler is regex-based, so it handles phrasings we anticipated and misses others. The mitigation is that everything it extracts is shown back before confirmation, so a bad reading is visible rather than silent. Two tuned numbers — familiarity at one prior purchase, a three-hour duplicate window — are judgements, not measurements.

“Would this scale?”

The engine is a pure function with no I/O, so it scales horizontally without coordination. Two things would not: familiarity currently loads all 4,701 history rows at import and should be a query, and the control session is a JSON file rather than a database.
